# Правила делегирования агентам

## Когда делегировать

| Ситуация | Агент | Причина |
|----------|-------|---------|
| Определение требований | `requirements-analyst` | Формализация acceptance criteria |
| Новая фича | `tdd-test-writer` | Принудительный test-first |
| Исправление бага | `tdd-test-writer` | Сначала тест воспроизводящий баг |
| Рефакторинг | `tdd-refactorer` | Безопасные изменения под защитой тестов |
| Тесты падают | `tdd-implementer` | Минимальный фикс для прохождения |
| Улучшение кода | `tdd-refactorer` | Улучшить без изменения поведения |
| Code review | `code-reviewer` | Проверка качества и стандартов |

## Критерии выбора агента

### Используй `requirements-analyst` когда:
- Начинаешь новую фичу (ANALYSIS фаза)
- Нужно уточнить acceptance criteria
- Требования неясны или неполны
- Нужно проверить Memory Bank на похожие фичи

### Используй `tdd-test-writer` когда:
- Requirements spec утверждён (после ANALYSIS)
- Исправляешь баг (сначала падающий тест!)
- Добавляешь покрытие к существующему коду

### Используй `tdd-implementer` когда:
- Тесты написаны и падают
- Нужна минимальная реализация для прохождения
- Тест воспроизводящий баг уже существует

### Используй `tdd-refactorer` когда:
- Все тесты проходят
- Качество кода нужно улучшить
- Очистка технического долга
- Добавление type hints или docstrings

### Используй `code-reviewer` когда:
- TDD цикл завершен
- Нужна проверка перед коммитом
- Ревью pull request

## Изоляция контекста

Каждый субагент работает в **изолированном контексте** для предотвращения загрязнения:

```
Главный контекст (ты)
    │
    ├── requirements-analyst (изолированный 200k контекст)
    │   └── Видит только: описание фичи, Memory Bank
    │
    ├── tdd-test-writer (изолированный 200k контекст)
    │   └── Видит только: requirements spec, паттерны тестов
    │
    ├── tdd-implementer (изолированный 200k контекст)
    │   └── Видит только: тест-файлы, сообщения об ошибках
    │
    ├── tdd-refactorer (изолированный 200k контекст)
    │   └── Видит только: реализацию, тест-файлы
    │
    └── code-reviewer (изолированный 200k контекст)
        └── Видит только: код, тесты, diff
```

**Почему изоляция важна:**
- Requirements analyst не видит существующий код (чистый взгляд)
- Test writer не знает деталей реализации
- Implementer не может "подсмотреть" логику дизайна тестов
- Refactorer смотрит на код свежим взглядом
- Code reviewer имеет независимую оценку

## Tasks API + Subagents: Координация

```
┌─────────────────────────────────────────────────────────────┐
│                   ДВУХУРОВНЕВАЯ КООРДИНАЦИЯ                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  TASKS API (Session Memory)                                 │
│  - Отслеживание прогресса: ANALYSIS → RED → GREEN → ...    │
│  - Enforcement зависимостей: blockedBy                      │
│  - Persist через context compaction                         │
│  - Управляется ГЛАВНЫМ агентом                              │
│                                                             │
│  SUBAGENTS (Isolated Execution)                             │
│  - Выполнение конкретной работы                             │
│  - НЕ видят Tasks (disallowedTools: Task)                   │
│  - Результат возвращается главному агенту                   │
│                                                             │
│  FLOW:                                                      │
│  1. Main agent: TaskUpdate → in_progress                    │
│  2. Main agent: "Use the X subagent to..."                  │
│  3. Subagent: выполняет работу                              │
│  4. Main agent: получает результат                          │
│  5. Main agent: TaskUpdate → completed + metadata           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Почему subagents не имеют доступ к Tasks:**
- Tasks — для координации, не для выполнения
- Subagent должен фокусироваться на одной задаче
- Предотвращает изменение статуса из неправильного контекста

## Синтаксис делегирования

**ВАЖНО:** Субагенты вызываются через естественный язык, НЕ через Task tool!

```
Use the requirements-analyst subagent to analyze requirements for email validation.

Use the tdd-test-writer subagent to write tests for user authentication.

Use the tdd-implementer subagent to implement minimal code to pass tests.

Use the tdd-refactorer subagent to improve code quality in src/auth.py.

Use the code-reviewer subagent to review changes before commit.
```

**НЕ ИСПОЛЬЗУЙ Task tool для субагентов:**
```
# НЕПРАВИЛЬНО:
Task(subagent_type="tdd-test-writer", ...)  # Task tool не поддерживает кастомных агентов

# ПРАВИЛЬНО:
"Use the tdd-test-writer subagent to..."  # Естественный язык
```

## Анти-паттерны

### НЕ ДЕЛАЙ: Пропускать ANALYSIS фазу
```
# ПЛОХО: "Требования понятны, сразу пишу тесты"
# Результат: тесты не покрывают все acceptance criteria
```

### НЕ ДЕЛАЙ: Пропускать агентов для "простых" изменений
```
# ПЛОХО: "Это просто маленькая функция, напишу напрямую"
# Это обходит TDD дисциплину
```

### НЕ ДЕЛАЙ: Использовать неправильного агента
```
# ПЛОХО: Использовать tdd-implementer ДО написания тестов
# ПЛОХО: Использовать tdd-refactorer когда тесты падают
```

### НЕ ДЕЛАЙ: Запускать несколько фаз в одном контексте
```
# ПЛОХО: Писать тесты и реализацию в главном контексте
# Это вызывает загрязнение контекста
```

## Параллельное выполнение

Для независимых фич запускай агентов параллельно:

```
Запусти 3 tdd-test-writer субагента параллельно:
1. Тесты для регистрации пользователя
2. Тесты для сброса пароля
3. Тесты для верификации email
```

Каждый агент получает изолированный 200k контекст.

## Нарушения фаз TDD

| Нарушение | Почему плохо | Как исправить |
|-----------|-------------|---------------|
| Пропуск ANALYSIS | Тесты неполные | Сначала requirements spec |
| Реализация до теста | Тесты ничего не доказывают | Всегда пиши тест первым |
| Изменение теста чтобы прошел | Скрывает баги | Fix code, not tests |
| Пропуск RED фазы | Не видишь что тест работает | Подтверди что тест падает |
| Рефакторинг с падающими тестами | Не знаешь что сломал | Сначала GREEN, потом REFACTOR |
